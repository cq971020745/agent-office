# 知识库问答

用通用知识库 MCP（`knowledge_*`）检索、读取和引用受权资料；先查后答，证据不足时说清楚边界。

## 判断与检索

| 问题 | 检索策略 | 输出 |
|---|---|---|
| 事实、会议决定、领导要求 | 主题加会议/讲话/决定词 | 结论和紧邻来源 |
| 最新口径、版本比较 | 主题分别检索日期、版本和权威文档 | 时间线、当前口径、差异 |
| 目录进展 | 方案、纪要、月报和推进记录联合检索 | 已完成、进行中、风险、下一步 |
| 材料清单、某篇长文的章节 | 先 `knowledge_search`（`topK` 12–16），必要时再 `knowledge_get_document` | 标题、目录路径；文本类展示 content |
| 原文、引语核对 | `knowledge_search` 定位后调用 `knowledge_get_document` | 文本类在对话里展示 `content`；Office/PDF 才给 `previewUrl` |
| 成段结论 | `knowledge_search` 后调用 `knowledge_answer` | 带来源的结论，不编造 |
| 写作素材 | 提取事实、口径、历史表述和风险 | 素材包，不直接替用户成稿 |

## 是否需要用户补充

不要把补充描述作为检索前置条件。先从用户问题和当前对话中提取可用条件，再用“元数据过滤 + 语义检索”直接查：

- `folder_id/folder_name/folder_path`：目录归属，也就是用户所称的事项；当前对话已明确目录时优先限定目录。
- `doc_type/topics/tags/period/status/version`：用于缩小候选文档范围；标签是辅助维度，不要求每个问题都必须有标签。
- 用户问题：用于正文语义检索，补足元数据没有表达的内容。

只有以下情况才向用户追问，而且只追问一个最影响结果的条件：

1. 同一问题对应多个空间或目录，且用户没有说明范围；
2. 同一主题存在多个时间、版本、状态或对象，直接返回可能混淆；
3. 首轮检索无结果或结果证据不足，无法确认用户指向；
4. 用户使用“这个/最近/那份/进展怎么样”等指代，而当前对话无法解析指代对象。

追问时展示 2 至 5 个候选目录、时间或文档标题，并提供“自定义/不限定范围”；不要让用户重新描述整段需求。若只有一个高置信度候选，直接回答并注明检索范围。

## 检索步骤

1. 提取主题、时间、领导、会议、文档类型和“最新”等限定词；能从问题中提取就直接使用，不为补充而补充。必要时先调用 `knowledge_list_spaces`，不猜空间 ID。`spaceId` / `directoryId` / `documentId` 为 `sp_` / `dir_` / `doc_` 前缀字符串，必须原样回传。
2. 使用 `knowledge_search` 进行第一轮检索；已知业务目录时传入 `directoryId`，已知分类时传入 `metadataFilters`。空筛选不要指望后端回退全库。盘点材料或覆盖长文后半章时把 `topK` 提到 12–16。
3. 检查命中数量、相关性、时间/版本一致性和来源是否集中。需要成段结论时用 `knowledge_answer`。`knowledge_answer` 只基于召回片段，默认也不会读完全文；漏掉「主要工作」一类后部章节时，不要反复只调 answer，改为加大 `topK` 的 search，或对目标文档调用 `knowledge_get_document`。
4. 用户要求原文、完整内容或核对引语时调用 `knowledge_get_document`：
   - Markdown / 纯文本：在对话里展示返回的 `content`，不要把存储地址交给用户去浏览器打开。`contentTruncated=true` 时说明未读全。
   - Office / PDF / 图片：没有 `content`，才把 `previewUrl` 交给用户打开。
   - 不要把检索摘要伪装为引号原文。
5. 生成前核对问题、日期、版本、决策状态和证据覆盖。

## 链接与预览

工作台预览 Markdown 是把原件下载后在弹窗里按 UTF-8 显示，**不会**让用户去打开 MinIO 地址。外部 Agent 对文本类必须同样处理：调用 `knowledge_get_document`，把 `content` 写进对话。

`previewUrl` 只给 PDF、图片、Office **原件**（约 7 天私有预签名，非转换 PDF）。主机名来自「对象存储」配置里的 endpoint/domain，不是知识库页面。本机开发常为 `127.0.0.1:9000`；上线后改成浏览器和 Agent 所在电脑都能访问的域名。直接打开 `.md` 预签名地址会乱码，不要当原文链接用。工作台本身对 docx/xlsx/txt/md 做浏览器原件渲染（ADR 0011）。

WorkBuddy 右侧「产物」里的 `.md` 是对话本地文件，不是知识库地址。

引用规则：

- Markdown/纯文本：对话内展示正文或片段，依据写标题 + 空间/目录 + documentId。
- PDF/Office/图片：原样给出 `previewUrl`，并注明约 N 天有效。
- 没有 `previewUrl` 时不编造、不拼接 `127.0.0.1` 或工作台地址。
- 不要把 `documentId` 转成 JSON 数字。

## 回答格式

```text
结论：...

依据：
1. ...（文档标题；空间/目录；文本类不附链接，PDF/Office 才附 previewUrl）
2. ...

未确认/需补充：...
```

按时间回答时，用“日期：变化（来源）”列时间线，再给出当前可确认口径。知识库无直接依据时说明已检索方向与建议补充资料；MCP 不可用时不伪造答案。

## 事实闸门

- 只基于返回的片段或已读 `content` 回答；区分已决定、建议、讨论中和草案。
- 保留返回的真实标题、位置、排名与链接；没有链接时不编造。
- 普通寒暄和非内部知识由上层 Agent 自然回复，不调用知识库。
